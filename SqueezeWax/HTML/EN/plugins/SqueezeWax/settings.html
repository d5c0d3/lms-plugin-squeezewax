Every action on this page defers its render until its own callback fires - _syncNow waits for the collection fetch, _testToken for /oauth/identity - so the browser sits on a pending POST with nothing to look at. The natural response to a button that looks dead is to press it again, which is how the dead-button bug was found in the first place. No core settings page does this. The nearest thing is settings/server/basic.html:11-30, which polls `rescan ?` on an Ext TaskRunner and disables anything carrying .disableOnScan. That is the polling shape this was explicitly decided against: it needs a server-side thing to poll, and these actions have none. So: no new server state, no polling, no framework. Plain DOM, and the page still works with JavaScript off - the buttons simply submit as they always did. Two subtleties, both learned the hard way. The hidden field: a disabled control is not part of the form data set, so disabling the clicked submit button removes the very name handler() dispatches on and every action would fall through to a plain save. The clicked button's name and value are copied into a hidden input BEFORE anything is disabled, so what reaches the server is identical either way. The deferred disable: disabling a submit button inside its own click handler does not merely drop its name, it cancels the submission outright. 0.0.0.5 shipped with a synchronous disable and the buttons became dead again - they greyed out, they relabelled, and nothing was ever sent. See the comment on the setTimeout below. %] [% PROCESS settings/footer.html %]
